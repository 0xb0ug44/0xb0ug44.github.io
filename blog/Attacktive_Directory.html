Attacktive Directory: From Kerberos Enumeration to Domain Admin

MY
Mohamed Yassine Bougamra
TryHackMe Active Directory Kerberos SMB
⚠️ Spoiler warning: this post contains the complete solution for the Attacktive Directory room. Try the room yourself first if you want to solve it without hints.

Attacktive Directory is an introductory Active Directory room that demonstrates how small enumeration mistakes can become a complete domain compromise. The attack chain moves from exposed Windows services to Kerberos user discovery, an AS-REP roastable account, sensitive data in an SMB share, and finally administrator access.

If you want to try the room yourself, you can access it on TryHackMe: Attacktive Directory.

This is the route I followed against the room target. Replace <target-ip> with the address assigned by TryHackMe and keep the lab scope in mind throughout the exercise.

Step 1: Mapping the Domain Controller

I started with a full TCP scan and service detection. Active Directory attacks depend heavily on the services exposed by the domain controller, so I did not limit the scan to the common web ports.

recon.shnmap
nmap -sC -sV -p- -T4 <target-ip>

The result identified a Windows domain controller, with DNS, Kerberos, LDAP, SMB, and WinRM among the important services. The room uses the domain spookysec.local, so I added the target to my local hosts file for tools that expect a hostname.

hosts.txtdns
<target-ip> spookysec.local

Step 2: Enumerating Domain Users with Kerberos

Kerberos accepts username requests before authentication is complete. That makes it possible to validate a candidate username list without guessing passwords.

user-enum.shkerbrute
kerbrute userenum --dc <target-ip> -d spookysec.local users.txt

The enumeration returned several valid domain accounts. I saved those names because they could be used for targeted Kerberos requests and later credential testing.

Step 3: Finding an AS-REP Roastable Account

Some domain accounts do not require Kerberos pre-authentication. When that setting is enabled, the Key Distribution Center returns material that can be cracked offline without knowing the user's password.

asrep-roast.shimpacket
GetNPUsers.py spookysec.local/ -dc-ip <target-ip> -usersfile users.txt -format hashcat -outputfile asrep.hashes

One account returned an AS-REP hash. I moved the cracking step offline and did not send password guesses to the domain controller.

crack.shhashcat
hashcat -m 18200 asrep.hashes /usr/share/wordlists/rockyou.txt

The recovered credential belonged to a low-privileged service account. It was enough to authenticate to SMB and enumerate the shares that were not available anonymously.

Step 4: Searching SMB Shares

I listed the shares with the recovered account, then connected to the interesting backup share.

smb-enum.shsmbclient
smbclient -L //<target-ip> -U <user>
smbclient //<target-ip>/backup -U <user>
ls
get backup_credentials.txt

The share contained a file with another set of domain credentials. This is a useful reminder that read access to a backup share can be as valuable as an executable foothold: configuration files and scripts often preserve passwords that have been reused elsewhere.

Step 5: Reusing the Recovered Credentials

I tested the new credentials against the domain services identified during reconnaissance. The account had stronger access than the original service account and could be used to request the domain's credential material.

secrets.shimpacket
secretsdump.py spookysec.local/<user>:<password>@<target-ip>

The dump exposed NTLM hashes for domain accounts, including the built-in administrator. I treated the hashes as sensitive lab output and stored them locally rather than including them in this walkthrough.

Step 6: Accessing the Domain Controller

After confirming that the administrator hash could authenticate to the available remote-management service, I used the recovered administrator credential to obtain an interactive session.

remote-access.shevil-winrm
evil-winrm -i <target-ip> -u Administrator -H <administrator-ntlm-hash>

The session ran with domain-administrator privileges. From there I verified the account context and collected the final room artifacts from the locations specified by the questions.

verify.ps1powershell
whoami
hostname
dir C:\Users\Administrator\Desktop

Key Takeaways

  • Full service enumeration is especially important against domain controllers.
  • Kerberos user enumeration can reveal valid accounts without password spraying.
  • AS-REP roasting turns a configuration weakness into an offline cracking opportunity.
  • SMB shares should be checked for backups, scripts, and credentials after every valid login.
  • Password reuse can turn a low-privileged service account into a path to domain compromise.
